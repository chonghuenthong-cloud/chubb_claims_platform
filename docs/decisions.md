# Architecture Decision Log

Short records of the key decisions: what was chosen, why, and what was given up.

## D1. Backend: Java 21 + Spring Boot 4.1
- **Why:** Java 21 was already installed; the Spring ecosystem covers REST, JPA, Kafka, security and OpenAPI with first-party starters.
- **Trade-off:** Spring Boot 4.1.3 was chosen over 4.2.0 because 4.2.0 had only just been released.

## D2. One service (modular monolith), Kafka consumers in-process
- **Why:** In a 2–5 hour sprint, every extra service adds a build, config, Docker image and failure mode. Package boundaries (`claim`, `policy`, `user`, `events`, `insights`, `notification`) keep the seams visible, so a module can be extracted later.
- **Kafka still does real work:** state changes publish domain events; consumers build the workload/exposure read model and claimant notifications. A slow or failing consumer cannot block a claim submission.
- **Trade-off:** One deployable means one scaling unit. Extraction is the documented next step.

## D3. PostgreSQL in Docker, schema managed by Flyway
- **Why:** Docker is already required for Kafka. Real Postgres behaves like production (constraints, numeric precision, sequences). Flyway makes schema changes reviewable and repeatable; Hibernate only validates against the schema.

## D4. Seeded users + simple JWT roles
- **Why:** Gives both user types with role-based access, at very low cost. A real identity provider (Keycloak, Entra ID) is the production path.

## D5. Code-first API, OpenAPI generated by springdoc
- **Why:** Faster to iterate. The backend owns the contract, and the generated spec at `/v3/api-docs` is the source the frontend builds against.
- **Trade-off:** Contract-first would let frontend and backend work in parallel from day one.

## D6. Domain model
- **Entities:** `AppUser`, `Policy`, `Claim`, `ClaimStatusHistory`, `InformationRequest`.
- **Decision data lives on `Claim`** (approved amount, rejection reason). A claim has at most one decision, so a separate table would add a join without adding information.
- **Liability exposure** = for open claims, `reserve_amount`; for approved-but-unsettled claims, `approved_amount`.
- **Optimistic locking** (`version` column) prevents two officers from overwriting each other's changes.

### Claim state machine
```
SUBMITTED → UNDER_REVIEW ⇄ AWAITING_INFO
UNDER_REVIEW → APPROVED → SETTLED
UNDER_REVIEW → REJECTED
```
`SETTLED` and `REJECTED` are terminal.

### Known gaps in the rules
- **Nothing links market to currency.** A Singapore policy could be stored in MYR. It is only correct today because the demo data was typed that way.
- **One coverage limit per policy.** Real motor policies have separate limits (own damage, third-party property, and so on).

### Known technical gaps
- **Lists are not paginated.** `GET /api/claims` and `GET /api/me/claims` return every matching claim in one response. Fine for demo data; at production volume the staff queue needs server-side paging. Planned together with work-queue filters ("unassigned", "assigned to me") in the staff milestone, since the two are used together. (Eunice, R10)

### Demo data (not rules)
Policy numbers, coverage limits, currencies, dates and users in `db/seed/V100__seed_demo_data.sql` were **invented by the AI for the demo**. They are not real Chubb figures. Example: Alice's `SG-MOT-0001` is a Singapore motor policy in SGD with a 50,000 limit.

## Assumptions (to confirm)
- **Two roles:** `CLAIMANT` and `STAFF`, matching the brief's "two user types". All staff can see the team dashboard; there is no separate manager role.
- **Single team:** no team table. All staff form one team.
- **Six markets:** the brief doesn't name them. Assumed SG, MY, TH, HK, ID, PH.
- **Currency:** each policy carries its own currency. Exposure totals are grouped by currency, with no FX conversion.
