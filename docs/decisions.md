# Architecture Decision Log

Short records of the key decisions: what was chosen, why, and what was given up.

## D1. Backend: Java 21 + Spring Boot 4.1
- **Why:** Java 21 was already installed; the Spring ecosystem covers REST, JPA, Kafka, security and OpenAPI with first-party starters.
- **Trade-off:** Spring Boot 4.1.3 was chosen over 4.2.0 because 4.2.0 had only just been released.

## D2. One service (modular monolith), Kafka consumers in-process
- **Why:** In a 2–5 hour sprint, every extra service adds a build, config, Docker image and failure mode. Package boundaries (`claim`, `policy`, `user`, `events`, `insights`, `notification`) keep the seams visible, so a module can be extracted later.
- **Kafka still does real work:** state changes publish domain events; consumers build the workload/exposure read model and claimant notifications. A slow or failing consumer cannot block a claim submission.
- **Trade-off:** One deployable means one scaling unit. Extraction is the documented next step.

## D3. PostgreSQL in Docker, schema managed by Flyway
- **Why:** Docker is already required for Kafka. Real Postgres behaves like production (constraints, numeric precision, sequences). Flyway makes schema changes reviewable and repeatable; Hibernate only validates against the schema.

## D4. Seeded users + simple JWT roles
- **Why:** Gives both user types with role-based access, at very low cost. A real identity provider (Keycloak, Entra ID) is the production path.

## D5. Code-first API, OpenAPI generated by springdoc
- **Why:** Faster to iterate. The backend owns the contract, and the generated spec at `/v3/api-docs` is the source the frontend builds against.
- **Trade-off:** Contract-first would let frontend and backend work in parallel from day one.

## D6. Domain model
- **Entities:** `AppUser`, `Policy`, `Claim`, `ClaimStatusHistory`, `InformationRequest`.
- **Decision data lives on `Claim`** (approved amount, rejection reason). A claim has at most one decision, so a separate table would add a join without adding information.
- **Liability exposure** = for open claims, `reserve_amount`; for approved-but-unsettled claims, `approved_amount`.
- **Optimistic locking** (`version` column) prevents two officers from overwriting each other's changes.

### Claim state machine
```
SUBMITTED → UNDER_REVIEW ⇄ AWAITING_INFO
UNDER_REVIEW → APPROVED → SETTLED
UNDER_REVIEW → REJECTED
```
`SETTLED` and `REJECTED` are terminal.

### Team dashboard (`GET /api/dashboard`, staff only)
All figures are **all-time** and calculated **live with SQL** on every request (`dashboard/DashboardService`). Tested with exact hand-calculated values from the seed data in `DashboardIntegrationTest`.

| Figure | How it's calculated | Decided |
|------|------|---------|
| Unassigned queue | Count of claims with no officer, and the oldest submission time (shown as "waiting X") | Eunice |
| Workload per officer | Each staff member's open claims: Under review, Awaiting info, Approved-not-settled, total. Idle officers show zeros | Eunice (D3) |
| Liability exposure | Per currency (no FX, B6): sum of reserves on open claims (Submitted, Under review, Awaiting info, Approved), split by market and by product. Rejected and settled claims have a reserve of 0 (S10) | Eunice |
| Approved / rejected / settled per officer | Counted from the status history: who made each change | Eunice (D5) |
| Submission → pick-up | Average of (pick-up entry − submission), credited to the officer who picked up | Eunice |
| Pick-up → decision | Average of (approve/reject entry − pick-up entry), credited to the officer who decided. **Includes time spent waiting for the claimant's answer**, so it measures total assessment time, not only officer effort | Eunice (added after the AI's first plan left it out) |
| Approval → settlement | Average of (settle entry − approve entry), credited to the officer who settled | Eunice |
| Display | Durations as hours under 1 day, otherwise days; "–" when there's nothing to average | Eunice (D7, F5) |

**Trade-off: live SQL vs a Kafka read model.** Live queries are always exact and add no moving parts, which suits this scale. At production volume (six markets, many officers), the dashboard would read from summary tables kept up to date by Kafka consumers of claim events, the design planned in D2. (Eunice)

### Known gaps in the rules
- **Nothing links market to currency.** A Singapore policy could be stored in MYR. It is only correct today because the demo data was typed that way.
- **One coverage limit per policy.** Real motor policies have separate limits (own damage, third-party property, and so on).

### Known technical gaps
- **Lists are not paginated.** `GET /api/claims` and `GET /api/me/claims` return every matching claim in one response. Fine for demo data; at production volume the staff queue needs server-side paging. The queue filters were built in the staff milestone; paging was deferred again because the demo has only a few claims. (Eunice, R10, S14)
- **Reserve changes are not audited.** The history table records status changes only, so a revised reserve keeps no record of who changed it, from what, or when. A reserve-change table is the fix. (Eunice, S9)
- **No reassignment.** If the assigned officer is away, nobody else can act on their claims. (Eunice: self pick-up only)
- **Actions don't publish Kafka events yet.** Planned for the Kafka milestone. (Eunice, S15)
- ~~Claimants can't see decisions yet.~~ **Closed** by the claimant tracking milestone: the claimant claim page shows the decision, timeline and questions. (Eunice, V9)
- **Dashboard has no time filter.** All figures are all-time; a period filter (7 / 30 / 90 days) would suit managers better at real volume.
- **Dashboard queries run on every page load.** Fine at this scale; would move to a Kafka-fed read model at production volume.
- **No live updates for claimants.** A claimant sees a decision only when they open or reload the app. Push notifications are planned with Kafka.
- **Stale screens aren't detected.** The UI doesn't send the claim version it loaded, so an officer acting on an old screen is only stopped by the status checks, not by a version mismatch. (Eunice, S12)

### Demo data (not rules)
Policy numbers, coverage limits, currencies, dates and users in `db/seed/V100__seed_demo_data.sql` were **invented by the AI for the demo**. They are not real Chubb figures. Example: Alice's `SG-MOT-0001` is a Singapore motor policy in SGD with a 50,000 limit.

## Assumptions (to confirm)
- **Two roles:** `CLAIMANT` and `STAFF`, matching the brief's "two user types". All staff can see the team dashboard; there is no separate manager role.
- **Single team:** no team table. All staff form one team.
- **Six markets:** the brief doesn't name them. Assumed SG, MY, TH, HK, ID, PH.
- **Currency:** each policy carries its own currency. Exposure totals are grouped by currency, with no FX conversion.
